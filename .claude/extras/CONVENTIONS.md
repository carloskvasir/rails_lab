This file is the canonical source for commit, branch and authorship conventions in this repository. It is referenced from [`CLAUDE.md`](./CLAUDE.md) so any AI agent operating on the repo picks up these rules automatically.

## 🔖 Commit Messages — Conventional Commits

Every commit message **must** follow the [Conventional Commits 1.0](https://www.conventionalcommits.org/) specification.

### Format

```
<type>(<scope>)?: <subject>

<body>

<footer>
```

- **type** — required, lowercase, one of the values below.
- **scope** — optional, lowercase, in parentheses. Use a folder or module name (`models`, `config`, `deploy`, `docs`, `infra`).
- **subject** — required, imperative mood, no trailing period, ≤ 72 characters.
- **body** — optional, separated by a blank line. Wraps at 100 characters. Explains the *why*, not the *what*.
- **footer** — optional. Used for `BREAKING CHANGE:` notes and issue references (e.g. `Refs: #12`).

### Allowed types

| Type | When to use |
|---|---|
| `feat` | A new feature visible to the user. |
| `fix` | A bug fix. |
| `refactor` | Code change that neither fixes a bug nor adds a feature. |
| `perf` | Performance improvement. |
| `docs` | Documentation only changes. |
| `style` | Formatting, whitespace, missing semicolons — no code behaviour change. |
| `test` | Adding or correcting tests. |
| `chore` | Build process, tooling, dependencies, or other auxiliary changes. |
| `ci` | Changes to CI configuration. |
| `build` | Changes to the build system or external dependencies (Dockerfile, Gemfile). |
| `revert` | Reverts a previous commit. |

### Breaking changes

Either append `!` after the type/scope (`feat!: drop support for Ruby 3.2`) **or** add a `BREAKING CHANGE:` footer. Both is fine.

### Examples

```
feat(models): add Account model with acts_as_tenant scoping

Introduces multi-tenant data isolation as the foundation for the
upcoming workspace feature. Tenant resolution is wired through a
custom middleware in config/initializers/multitenant.rb.

Refs: #4
```

```
fix(deploy): bind Puma to 0.0.0.0 inside Kamal container

Railway's healthcheck was failing because Puma defaulted to
localhost. Switching the bind address restores zero-downtime
deploys.
```

```
chore(infra): bootstrap Rails 7.2.3.1 application

Generated via `rails _7.2.3.1_ new . -d postgresql --skip-docker
--skip-kamal --skip-bundle`. Skip flags preserve the pre-existing
Dockerfile and config/deploy.yml.
```

## 👤 Authorship Rules

These rules apply to **every commit** made in this repository, by humans or AI agents alike.

1. **Author = the human owner of the workstation.** Commits are authored by the developer whose `git config user.name` / `user.email` is configured globally on the machine — currently `Carlos Kvasir <gpg@kvasir.dev>`.
2. **No AI attribution in the commit metadata.** Do not set `--author`, do not add `Co-Authored-By: Claude …`, `Co-Authored-By: Gemini …`, or any other AI attribution trailer. The commit must be indistinguishable from one the human wrote by hand.
3. **No AI attribution in the commit message body.** Do not write things like *"Generated by Claude"*, *"AI-assisted"*, or *"🤖 Generated with …"*. The message describes the change, not who typed it.
4. **No tool emoji or signature footers.** No 🤖, no ✨, no `Generated-By:`, no `Tool: claude-code`. Plain Conventional Commits only.
5. **Do not modify `git config`.** AI agents must never run `git config --global` or `git config --local` to change identity. If the configured identity is wrong, ask the user to fix it manually.
6. **Sign-off is optional.** This repo does not require DCO sign-off. If the user requests `-s`, honour it.

### Why these rules

Lab commits flow into public history (and eventually a production-grade pipeline). Mixing AI attribution into the metadata pollutes `git blame`, breaks ownership signals for code review tooling, and creates noise for any future contributor parsing the log. The human is accountable for what they commit; the tool used to type it is not part of that record.

## 🌿 Branches

Branches **must** follow the following naming pattern:
`<type>/<identifier>/<slug>`

- **type** — `feat`, `chore`, `fix`, or `security`.
- **identifier** — task ID in the format `rl-xxx` (e.g., `rl-123`, `rl-001`).
- **slug** — short, descriptive lowercase text (e.g., `create-anything`).

**Examples:**
- `feat/rl-001/create-anything`
- `fix/rl-111/login-error`
- `chore/rl-999/update-dependencies`

## 🔁 PR Titles

PR titles follow the same Conventional Commits format as commits, because the PR title becomes the squash-merge commit message.

## ✅ Pre-commit checklist (manual until automated)

Before every commit, verify:

- [ ] `bundle exec rubocop -A` is clean (once Rails app is bootable).
- [ ] `bin/rails test` is green (once tests exist).
- [ ] No `.env`, no `config/master.key`, no `*.pem`, no `tmp/` artefacts staged.
- [ ] No AI attribution in the message or trailers.
- [ ] Subject line is in imperative mood and under 72 chars.

A pre-commit hook will eventually enforce items 1–3; for now they are on the human committer.
